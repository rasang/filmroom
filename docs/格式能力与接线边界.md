# 格式能力模型（不是新增格式已验收声明）

## 当前代码与接线

`io/formats` 提供识别提示、能力模型和平台查询适配器。这些模型与实际读写路径必须分开判断：目录出现 HEIF、AVIF、WebP 等名称，不代表应用已支持。当前应用接入 JPEG / PNG 导入、原生编解码器支持的 DNG 子集，以及 JPEG / PNG / 16 位 TIFF 输出；具体原生限制以编解码器合同和对应测试记录为准。导出菜单依据实际原生库是否可用显示格式，不能单凭扩展名或系统声明开放选项。

```kotlin
val snapshot = AndroidFormatCapabilities.inspect(
    integrations = CodecIntegrations(), // 默认仅已有 JPEG / PNG 路线
    native = NativeCodecAvailability(), // 必须由实际原生探测结果填充
)
val heif = snapshot.importFor(PhotoFormat.HEIF)
// heif.platformDecoderPresent 与 heif.platformImplemented 是两个不同事实。
// canAttemptPreview / canAttemptOriginal 都仅意味着可尝试，具体文件仍可能失败。
val png = snapshot.exportFor(OutputEncoding.PNG)
// canAttemptBoundedBitmap 与 canAttemptOriginalStreaming 不能混用。
```

`CodecIntegrations` 必须由集成者在真实路线接通后显式登记；不能由手机版本号、文件后缀或库文件存在自动填充。`NativeCodecAvailability` 只接受枚举集合，适合把 RAW/DNG/TIFF/OpenEXR 的实际库探测结果映射进来。原生能预览不代表能输出原尺寸，也不代表已接入导出。

## 平台规则

- `ImageDecoder.isMimeTypeSupported` 自 API 29 可用。HEIF 是可选设备能力，应查询 `image/heif`；肯定结果不能保证任意位深、编码参数或分辨率，也不能证明原尺寸方向处理正确。[平台格式表](https://developer.android.com/media/platform/supported-formats)、[ImageDecoder API](https://developer.android.com/reference/android/graphics/ImageDecoder#isMimeTypeSupported(java.lang.String))
- 该平台表另有重要细节：API 31 起的 AVIF 基础 8 位解码，与可选 10 位能力不同；`image/avif` 查询为 false 不足以断言基础 8 位不可读。因此模型保留 `AVIF_BASELINE_8_BIT_API31`，没有把它称为实测支持，也不会默认接通 AVIF。[平台格式表](https://developer.android.com/media/platform/supported-formats)
- 当前 `BitmapRegionDecoder` 文档列出 JPEG、PNG、WebP、HEIF、AVIF，但不是每台旧设备的逐项原尺寸测试记录。模型对 AVIF 还设 API 31 门槛，仍要求每个文件真实创建 region decoder、校验条带尺寸和方向；不得回退到巨大整图 Bitmap。[region API](https://developer.android.com/reference/android/graphics/BitmapRegionDecoder)
- Bitmap 编码是另一个能力：JPEG、PNG、WebP；HEIF/AVIF 不能由 `Bitmap.compress` 编出。HEIF 需另接 MediaCodec/HeifWriter；AVIF 编码亦需相应实际编码路线。这些尚未接线时不显示为可选导出。[平台格式表](https://developer.android.com/media/platform/supported-formats)
- Android 10 的旧 `WEBP` 编码器以 quality=100 表示无损，0–99 才是有损；API 30 起用明确的 `WEBP_LOSSY` / `WEBP_LOSSLESS`。模型把这三种语义分开，不能把 API 29 的“有损100”悄悄编码成无损。[Bitmap.CompressFormat](https://developer.android.com/reference/android/graphics/Bitmap.CompressFormat)

## 识别、动画与精度

`PhotoHeaders.sniff(prefix, count)` 最多检查 64 KiB，输出只有枚举和有限数值；不使用文件名、扩展名、外部 MIME 或日志自由文本。识别 JPEG / PNG / WebP / HEIF / AVIF / GIF / BMP、TIFF 家族与 EXR。TIFF magic 只能认容器，**不能区分普通 TIFF、DNG 或部分相机 RAW**，须交实际原生解析器确认。BMFF 只解析完整有界 `ftyp` 的 major/compatible brands，不搜索任意文本，不把 minor_version 当 brand。[AVIF brands](https://aomediacodec.github.io/av1-avif/latest-approved.html)

这些都是头部提示，不做 CRC、完整容器或像素有效性证明，不得从提示中的尺寸分配内存。截断、未知、超长结构保守返回未知。不能由于找不到动画标记就声称一定是静态图。当前提示识别 WebP VP8X 动画位、APNG 的 acTL、HEIF/AVIF 序列 brands；GIF 头无法判定帧数。[WebP 容器规范](https://developers.google.com/speed/webp/docs/riff_container)、[PNG 规范](https://www.w3.org/TR/png-3/)

接入时应在真正解码前拒绝已识别动画/序列，并在 ImageDecoder 回调检查 `ImageInfo.isAnimated`，不能默默拿首帧当作完整照片。若前缀内不能决定是否 APNG，需另做有界逐块扫描或明确不接该类文件；不能假定 Android 必然识别全部 APNG 动画。[ImageInfo.isAnimated](https://developer.android.com/reference/android/graphics/ImageDecoder.ImageInfo#isAnimated())

当前平台照片处理路线有 sRGB、ARGB8、白色透明合成策略。导出 PNG“无损”仅指编码本次 8 位输出，不代表保留原高位深、广色域、HDR 或透明通道。原生 RAW/TIFF/EXR 的精度策略单独由实际 codec 合同确认。

## 测试范围

- `PhotoHeadersTest`：纯合成头字节，含截断、溢出、伪品牌、64 KiB 上限和随机输入；它们不是声称可解码的完整照片。
- `FormatCapabilitiesTest`：注入真假/异常 MIME 响应，验证接线与 runtime 必须同时成立、原尺寸/预览分离、导入/编码分离、可选 HEIF、AVIF 基础能力和 WebP 版本语义。
- Android 适配器可编译；本次**未运行设备/模拟器格式检测、HEIF/AVIF 实际像素或原尺寸验证**。现有 NativeGraphics JPEG/PNG 导入证据与纯 Kotlin PNG 编码证据不能替代上述未执行项目。
